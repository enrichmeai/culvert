Architecture spine · Sprint 23 · Epic 1

Job control and the audit trail were never two things

They were one thing modelled twice — which is how four incompatible shapes for a single table name came to exist. This is the spine that collapses them, and what four reviewer lenses found wrong with it before any code was written.

Decision (A) — the contract is normative Gate 4 lenses, 4 returned changes Status revised, awaiting scope call Date 4 Sep 2026

01The reframe

Story 1.4 stalled because docs/CONTRACT.md and the shipped code described the same table four incompatible ways. The way out was not picking a winner — it was noticing what §4 already says.

Contract §4 — event_kind

  • RUN_START
  • RUN_END
  • RECORD_VALIDATED
  • RECORD_REJECTED
  • RECONCILIATION
  • ERROR_RAISED
  • RETRY_ATTEMPTED

Highlighted values

Those five are the job-control lifecycle — createJob, updateStatus, markFailed, markRetrying — under different names.

Consequence

audit_events is the job-control log. pipeline_jobs becomes a projection over it, and the append-only requirement falls out for free.

02What the gate caught

Four independent lenses reviewed the draft. Every load-bearing claim was then re-verified against the code before being accepted — three of the architect's own decisions turned out to be factually wrong.

Critical

Two safe decisions that delete data together

Neither AD-2 (append-only) nor AD-3 (failure wins) is wrong alone. Chained, they reach a DELETE on a run that succeeded.

01
Today, SUCCEEDED requires a prior state of RUNNING — a compare-and-set that blocks late events from flipping a finished run. BigQueryJobControlRepository.java:613–617
02
AD-2 removes compare-and-set. Append-only stores have no prior state to test against.
03
AD-3 makes failure win. A late first ERROR_RAISED now makes a successful run read as FAILED.
04
FAILED is retryable, so the retry path calls cleanupPartialLoad. :618–621 → RetryOrchestrator.java:111
05
DELETE FROM <targetTable> WHERE _run_id — the successful run's data is gone. BigQueryJobControlRepository.java:541

Fixed by making terminal states immutable: once a run is terminal, later contradicting events are recorded but never change the projection, and never make it retryable.

Silent no-op

ignore_changes = [schema] on both job_control tables

The DDL work would have planned green and changed nothing — a silent success, in the very tool this epic uses to fix silent failures. Must be removed before any schema work begins.

Live bug

Duplicate Dataflow launches are happening today

JobStatus emits lowercase running/succeeded; fdp-trigger/dedup.py:38 filters status IN ('RUNNING','SUCCESS') — wrong case, and 'SUCCESS' is not a member at all. The query matches zero rows and raises nothing. Independent of this rebuild; wants its own issue.

Shadow model

Two writers already bypass the port

fdp-trigger and postgres-cdc-streaming write pipeline_jobs directly. AD-1 forbids a shadow job-control model; two instances already exist.

Author error

AD-6 contradicted the contract it implemented

§9 mandates RETRY_ATTEMPTED before each retry, capped at three — so keying idempotency on (run_id, event_kind) would have collapsed three required events into one. Also corrected: AD-9 cited a divergence between two declarations that are identical, and the stack table named an AWS SDK property that does not exist.

05Sequence

Numbered because it genuinely is one — phase 3 can lose data and is gated on phase 2 finishing.

0

Unblock

Remove ignore_changes; fix the dedup bug on its own issue; prove the emulator tier runs at all. Nothing downstream is trustworthy without these.

1

audit_events greenfield safe

Event type, fixtures before emitters, payload key contract, corrected table target. Closes Story 1.6.

2

Writers come inside the port

Must precede phase 3: a streaming insert against a projection hard-fails, and fdp-trigger's fires after the Dataflow launch has committed.

3

pipeline_jobs becomes a projection risky

Readers move first, one at a time. Terminal-immutability lands with this phase — append-only without it is worse than the mutable store it replaces.

4

Multi-cloud

Behavioural contract test, then BigQuery, DynamoDB and a new Athena implementation. Verified feasible — Athena supports INSERT INTO on non-Iceberg tables.

5

Consumers and the deferred sections

Grafana ported. §6 has no producer but five panels query it; §5 has six. Neither is free, and both are contract decisions.

06What needs a decision

  1. Split the epic? Landing both halves together means the safe half waits on the risky one, and a single revert takes out both.
  2. The two live bugs — separate issues? Duplicate Dataflow launches and the bypass writers exist independently of this work. Absorbing them into a refactor hides both.
  3. How does contract_version bump? §2 has no bucket for a per-row → per-run semantic change, and §11's process requires fixtures that phase 1 is what creates.
